# Шаблон чат-бота для мессенджера MAX

Готовая основа для ботов на платформе [MAX](https://max.ru) с настроенным
CI/CD под **GitHub Actions** и **Gitea Actions**. Собран из production-кода
двух работающих ботов: справочного (stateless, навигация по каталогу) и
модераторского (Postgres, миграции, админ-панель).

Шаблон закрывает то, что в каждом новом боте приходится писать заново:
ограничение частоты запросов к API, корректное завершение процесса, разбор
конфигурации с проверками, режимы polling/webhook, сборка образа и деплой с
откатом. Из коробки это бот-визитка: дерево разделов меню (текст, картинка,
кнопка-ссылка) целиком правится в **админке внутри MAX** — команда `/admin`,
без правки кода и передеплоя. Как пользоваться админкой —
[руководство администратора](docs/admin-guide.md).

## Быстрый старт

```bash
cp .env.example .env          # задать MAX_BOT_TOKEN и ADMIN_IDS
make install                  # uv sync
make up-local-db              # Postgres в Docker на 127.0.0.1:5433
make run                      # миграции + запуск в режиме polling
```

Или всё в Docker: `make up-local` (бот и Postgres, миграции при старте
контейнера). Токен бота выдаёт `@masterbot` в мессенджере MAX. Свой `user_id`
бот покажет по команде `/id` — впишите его в `ADMIN_IDS` и перезапустите.
Затем `/admin` в личке с ботом.

По умолчанию `PROD=false` — бот отвечает только тем, чьи id перечислены в
`ADMIN_IDS`. Это защита от преждевременного выхода к пользователям: пока бот
не настроен, посторонний увидит заглушку.

## Создание нового проекта

```bash
make init
```

Скрипт спросит имя (kebab-case) и описание, затем:

- подставит имя в `pyproject.toml`, оба compose-файла и пайплайн Gitea;
- заменит README заготовкой, а этот файл сохранит как `docs/TEMPLATE.md`;
- удалит сам себя;
- начнёт историю git заново одним коммитом (`--keep-git` отключает).

Неинтерактивно:

```bash
uv run python scripts/init_project.py --name support-max-bot --description "Бот техподдержки"
```

После инициализации разделы и приветствие задаются в админке (`/admin`).
Стартовое демо-наполнение — `SEED` в начальной миграции
`migrations/versions/*_initial.py`; его можно заменить своим до первого
деплоя.

## Конфигурация

Все параметры читаются из окружения (или `.env` в корне). Полный список с
пояснениями — в [`.env.example`](.env.example); ниже основное.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `MAX_BOT_TOKEN` | — | **Обязательна.** Токен бота |
| `BOT_MODE` | `polling` | `polling` или `webhook` |
| `PROD` | `false` | `false` — только администраторы, `true` — все |
| `ADMIN_IDS` | пусто | user_id через запятую |
| `LOG_LEVEL` | `info` | debug/info/warning/error |
| `PORT` | `8081` | Порт webhook-сервера |
| `WEBHOOK_HOST` | — | Обязательна при `BOT_MODE=webhook` |
| `WEBHOOK_SECRET` | — | Обязательна при `BOT_MODE=webhook` |
| `MAX_API_RPS` | `25` | Общий лимит запросов к API |
| `MAX_API_MESSAGE_RPS` | `2` | Лимит отправки сообщений |
| `MAX_CA_BUNDLE` | — | Путь к дополнительному корневому сертификату |
| `DATABASE_URL` | — | **Обязательна.** DSN Postgres (`postgresql+asyncpg://…`) |
| `POSTGRES_PASSWORD` | `bot` | Пароль Postgres в compose; на проде обязателен |
| `STATS_ENABLED` | `true` | Записывать открытия разделов |
| `STATS_SALT` | пусто | Секрет хеша посетителей; пусто — `MAX_BOT_TOKEN` |
| `DISPLAY_UTC_OFFSET` | `3` | Часовой пояс времени в админке, часов от UTC |
| `METRICS_ENABLED` | `false` | HTTP-сервер метрик |
| `BUILD_TAG` | пусто | Заполняется при деплое, показывается в `/v` |

Конфигурация проверяется при старте, а не при первом обращении: бот не
запустится с webhook без секрета или с синхронным DSN. Ошибка на старте
дешевле, чем открытый эндпоинт или падение под нагрузкой.

## Режимы работы: polling и webhook

**Polling** (`BOT_MODE=polling`) — бот сам опрашивает платформу. Ничего не
слушает, публичный адрес не нужен. Режим для разработки.

**Webhook** (`BOT_MODE=webhook`) — платформа шлёт апдейты на ваш адрес. Бот
поднимает FastAPI, регистрирует подписку при старте и отдаёт `/healthz`.

Что нужно для webhook:

```bash
BOT_MODE=webhook
WEBHOOK_HOST=https://bot.example.ru      # публичный https без пути
WEBHOOK_SECRET=$(openssl rand -hex 32)   # обязателен
PORT=8081
```

Секрет обязателен намеренно. Библиотека `maxapi` проверяет заголовок
`X-Max-Bot-Api-Secret` только когда секрет задан — иначе эндпоинт принимает
любой POST от кого угодно. Шаблон отказывается стартовать в такой
конфигурации, чтобы дыра не уехала на прод незамеченной.

### Обработка апдейтов вебхука

Маршрут вебхука (`bot/webhook.py`) отвечает MAX сразу, а обработка уходит в
фоновую задачу — HTTP-соединение не удерживается на всё время работы
хендлера. Штатный маршрут `maxapi` делает наоборот (`dp.handle` прямо внутри
POST-запроса), из-за чего на всплеске сообщений соединения копятся, платформа
переотправляет апдейты новыми — и процесс упирается в лимит файловых
дескрипторов (`OSError: [Errno 24] Too many open files`).

Очередь фоновой обработки ограничена `WEBHOOK_MAX_PENDING_UPDATES`: сверх
лимита новые апдейты получают 503 (MAX повторит доставку), а не копятся в
открытых сокетах. Текущий размер очереди виден в `/healthz` полем
`pending_updates`. При остановке бот ждёт `WEBHOOK_DRAIN_TIMEOUT` секунд,
чтобы дообработать уже принятое.

### Про дубли апдейтов

Платформа повторяет апдейт, если не получила подтверждение вовремя.
Дедупликации по `update_id` в шаблоне **нет** — если ваши обработчики
выполняют неидемпотентные действия (списание, запись в БД, отправка
уведомления), добавьте её сами.

## Уровни доступа

1. **Maintenance-гейт** (`middlewares/maintenance.py`) — при `PROD=false`
   пропускает только владельцев (`ADMIN_IDS`). Работает как outer middleware, то есть до
   фильтров: перехватывает сообщения, нажатия кнопок и `bot_started` одним
   кодом. В группах при блокировке молчит — отвечать на каждое упоминание
   значит спамить чат.

2. **Ограничение частоты** (`middlewares/throttling.py`) — не чаще одного
   события на пользователя в 0.5 с. Состояние хранится в памяти процесса,
   поэтому при нескольких репликах лимит становится приблизительным; для
   честного распределённого лимита нужен Redis.

3. **Роли админки** (`handlers/admin.py`): `is_owner` — `ADMIN_IDS` из
   `.env`, права не зависят от БД, поэтому без администраторов бот не
   остаётся; `is_admin` — владелец или запись в таблице `staff`, читается из
   БД на каждом событии (отзыв действует сразу). Добавлять и отзывать
   администраторов может только владелец. Декоратор `admin_only` закрывает
   служебные команды: неадминам они не отвечают вовсе — сообщение
   «недостаточно прав» само раскрывает наличие скрытых функций.

## Как добавить функциональность

### Новый раздел меню

Через админку: `/admin` → **➕ Добавить подраздел**. Код не меняется.

### Новая команда

```python
# src/bot/handlers/my_feature.py
from maxapi import Dispatcher
from maxapi.filters.command import Command
from maxapi.types.updates.message_created import MessageCreated


def register(dp: Dispatcher) -> None:
    dp.message_created(Command("mycommand"))(on_my_command)


async def on_my_command(event: MessageCreated) -> None:
    await event.message.answer(text="Ответ")
```

Затем добавить `my_feature.register(dp)` в `handlers/__init__.py` — **до**
`menu.register(dp)`, иначе catch-all на свободный текст перехватит команду
раньше.

### Новый тип кнопки

Опишите payload классом в `keyboards/callbacks.py` (по образцу `SectionPayload`)
и обработайте его отдельным хендлером до `menu.register(dp)`: у `menu` callback
без фильтра и забирает всё, что не перехватили раньше. Формат payload задан в
одном месте намеренно: иначе рассинхрон между кнопкой и её обработчиком
всплывает только в рантайме, у пользователя.

## Админка в MAX

Весь пользовательский контент — дерево `sections` в Postgres. Корень — главное
меню: его текст — приветствие на `/start`, дочерние разделы — кнопки. Раздел
с `url` — кнопка-ссылка наружу; `image_token` — картинка над текстом (токен
фото, присланного в админку: MAX разрешает отправлять то же вложение
повторно, файл бот не хранит).

- **Пользователь** (`handlers/menu.py`): кнопка `s:<id>` меняет то же
  сообщение (`show_in_place`), «Назад» — кнопка родителя. Новое сообщение
  шлётся, только если править нечего или MAX ответил 4xx; на 5xx — нет, правка
  могла пройти после ретраев. Кнопка удалённого раздела даёт главное меню.
- **Админка** (`handlers/editor.py`): кнопки `a:<действие>:<цель>`, права
  проверяются на каждом нажатии. Название, текст, ссылку, картинку и файл
  админ присылает следующим сообщением (`pending.waiting`, только из лички,
  команды за ввод не считаются). Ожидание хранится в памяти процесса: при
  рестарте сбрасывается, при нескольких репликах нужна таблица.
- **Инструменты** (`handlers/tools.py`): администраторы, статистика
  (`section_views`, HMAC-хеш вместо user_id, админы не считаются), выгрузка и
  загрузка дерева JSON-файлом с проверкой как у ручного ввода, журнал
  (`audit_log`, пишется в транзакции правки).

Лимиты MAX: подпись кнопки до 64 символов, сообщение до 4000, ссылка до 2048,
до 30 рядов кнопок — поэтому подразделов не больше `MAX_CHILDREN = 24`.

## База данных

Postgres обязателен: в нём разделы, администраторы, статистика и журнал.
Драйвер — асинхронный (`+asyncpg`), синхронный DSN отклоняется при старте.
Контейнер бота перед запуском выполняет `alembic upgrade head`: свежая база
получает схему и демо-разделы, существующая — только новые ревизии.

```bash
make up-local-db                          # поднять Postgres в Docker
make migration m="добавил таблицу"        # создать ревизию
make migrate                              # применить
```

`alembic.ini` не содержит DSN — он берётся из настроек приложения, чтобы
креды не жили в двух местах. Весь SQL — в `db/repositories/`; обработчики к
сессии напрямую не ходят:

```python
from bot.db.repositories import SectionRepository
from bot.db.session import session_scope

async with session_scope() as session:  # commit при успехе, rollback при ошибке
    root = await SectionRepository(session).root()
```

В проде база видна боту по уникальному алиасу `max-bot-template-db`: бот
подключён ещё и к общей сети `maxbots-network`, где короткое имя `db` могло
бы совпасть с базой другого бота.

## Docker

Образ многостадийный (`docker/Dockerfile`):

- **base** — зависимости и код; отдельный слой на `pyproject.toml`, чтобы
  правка кода не тянула переустановку пакетов;
- **test** — доставляет dev-зависимости и гоняет линт с тестами; эту цель
  использует CI, проверяя ровно ту среду, что поедет на прод;
- **runtime** — прод-образ: без dev-зависимостей, от непривилегированного
  пользователя (`appuser`, uid 10001).

### Compose

`docker-compose.local.yml` собирает образ из исходников — разработчику нужно
видеть свои правки. Postgres вынесен в профиль `db` и без него не поднимается.

`docker-compose.prod.yml` тянет готовый образ из Harbor по тегу, выставляет
лимиты памяти и CPU и публикует бота через внешнюю сеть `maxbots-network`,
а не пробросом порта на хост.

Оба файла принимают `--env-file .env` — это обязательно. Без флага Compose
ищет `.env` рядом с самим compose-файлом, то есть в `docker/`, и подстановка
`${PORT}` в `ports:` молча берёт значение по умолчанию. Директива `env_file:`
внутри файла — другой механизм: она передаёт переменные в контейнер и
подстановку в YAML не заменяет. Makefile подставляет флаг сам.

Healthcheck в прод-конфигурации бьёт в `/healthz` и потому работает только
при `BOT_MODE=webhook`. Для polling его нужно убрать, иначе исправный бот
будет помечен `unhealthy`.

## CI/CD

### GitHub Actions (`.github/workflows/ci.yml`)

Три задачи: `lint` → `test` → `build`. Сборка проверяет валидность обоих
compose-файлов, собирает образ и публикует его в GHCR (на pull request —
только собирает, без публикации). Теги: `latest` на дефолтной ветке,
семантические на `v*.*.*`, `sha-<short>` всегда.

### Gitea Actions (`.gitea/workflows/pipeline.yml`)

Один файл на весь цикл: `lint` → `test` → `build` → `release-image` →
`deploy` → `rollback`.

**Почему один файл, а не ci.yml + cd.yml.** В Gitea Actions нет события
`workflow_run` ([gitea#24898](https://github.com/go-gitea/gitea/issues/24898)),
поэтому запустить деплой «после успешного CI» из отдельного файла нечем.
Единственный рабочий способ выстроить зависимость — `needs:` внутри одного
файла. Здесь `deploy` физически не стартует без успешных `lint`, `test` и
`build`.

Не добавляйте рядом второй workflow с теми же триггерами: Gitea запускает
каждый файл в `.gitea/workflows/` независимо, и вы получите двойные прогоны.

**Что происходит при пуше тега `vX.Y.Z`:**

1. `build` собирает образ и публикует его как `sha-<short>`;
2. `release-image` находит этот образ и перетегивает в `vX.Y.Z` без
   пересборки (если не нашёл — собирает из исходников тега);
3. `deploy` копирует compose на прод-хост, сохраняет предыдущий тег в
   `.image_tag.previous`, делает `pull` и `up -d`, затем проверяет, что
   контейнер запущен и не уходит в рестарт-петлю;
4. `rollback` срабатывает автоматически при провале и возвращает предыдущий
   тег.

Файл `.env` через пайплайн не ходит: боевые секреты лежат на прод-хосте
постоянно.

**Требуемые Gitea Variables:** `HARBOR_REGISTRY`, `HARBOR_PROJECT`,
`HARBOR_IMAGE`, `RUNNER_LABEL`, `PROD_HOST`, `PROD_USER`, `PROD_PATH`,
`NEXUS_URL` (опц.), `INSTALL_EXTRAS` (опц.).

**Требуемые Gitea Secrets:** `HARBOR_USERNAME`, `HARBOR_PASSWORD`,
`SSH_PRIVATE_KEY`, `NEXUS_USERNAME` / `NEXUS_PASSWORD` (опц.).

### Про smoke-тест образа

Полный старт бота в CI не проверяется: с плейсхолдер-токеном первый же запрос
к API вернёт 401, и гейт был бы красным при полностью исправной сборке.
Вместо этого проверяется импорт пакета внутри готового образа — он тянет все
зависимости и строит конфигурацию, то есть ловит именно ошибки сборки, без
сети и без реального токена.

## Закрытый контур

Шаблон настроен на работу за периметром, но остаётся работоспособным снаружи.

**По умолчанию** источники указывают на внутренние зеркала: `harbor.volganet.ru`
(образы), `nexus.volganet.ru` (PyPI и APT), `gitea.volganet.ru` (хуки
pre-commit). Все они параметризованы.

**Сборка с доступом в интернет:**

```bash
BASE_IMAGE=python:3.12-slim-bookworm \
UV_IMAGE=ghcr.io/astral-sh/uv:latest \
POSTGRES_IMAGE=postgres:16-alpine \
USE_NEXUS_APT=0 \
make up-local
```

Workflow для GitHub уже собирает с публичными источниками — у его раннера
доступа к контуру нет.

**Бинарь uv.** Раннер Gitea не может скачать uv с astral.sh, поэтому архив
кладётся в репозиторий — см. [`build/uv/README.md`](build/uv/README.md). Без
него задачи `lint`, `test` и `build` в Gitea упадут на распаковке.

**Сертификаты.** Если цепочка API подписана УЦ, которого нет в системном
хранилище (например, Минцифры РФ), есть два пути — положить `.crt` в
`certs/` (действует на весь контейнер) или указать `MAX_CA_BUNDLE`
(действует только на соединения бота). Подробности в
[`certs/README.md`](certs/README.md).

**Пароли в индексе.** `INDEX_URL` содержит креды Nexus. В пайплайне он
маскируется и передаётся через окружение шага; в `ENV` Dockerfile его
записывать нельзя — значение осело бы в метаданных образа открытым текстом.

## Тесты

```bash
make test
```

Разбор и валидация конфигурации, payload'ы кнопок, ограничитель частоты,
throttling, очередь вебхука, репозиторий разделов, сценарии админки
(`tests/test_editor_flow.py`, картинки — `tests/test_editor_images.py`) и инструментов (`tests/test_tools.py`):
администраторы, статистика, экспорт/импорт, журнал.

Хендлеры вызываются напрямую с заглушками событий (`FakeMessage`,
`FakeCallback`), maxapi-диспетчер не мокается. БД — SQLite в памяти из фикстуры
`sessionmaker` (с `PRAGMA foreign_keys`, ради каскада); фикстура `db` подменяет
`bot.db.session.get_sessionmaker`, поэтому `session_scope` во всех модулях
идёт в неё, а не в Postgres. Миграции на SQLite не прогоняются: схему
проверяет `alembic check` против Postgres.

Тесты герметичны: в сеть не ходят, реальный токен не используют, локальный
`.env` игнорируют (иначе они падали бы только у того разработчика, у кого
файл заполнен иначе).

Фикстура `env` из `tests/conftest.py` задаёт переменные окружения так же, как
это делает прод, — заодно проверяется и сам разбор конфигурации:

```python
def test_admin_ids_parsing(env) -> None:
    settings = env(ADMIN_IDS=" 123, 456 ,789 ")
    assert settings.admin_ids_set == frozenset({123, 456, 789})
```

## Решения, заложенные в шаблон

Короткий список того, что было выяснено на работающих ботах и перенесено сюда
вместе с причинами.

**Два независимых лимита на API.** Общий троттлинг (25 RPS) спасает от HTTP
429. Но у отправки и удаления сообщений есть отдельный антиспам-порог, за
превышение которого платформа блокирует бота, а не отвечает ошибкой — отсюда
второй, более строгий лимит именно на них.

**429 опознаётся по `ContentTypeError`.** При превышении лимита MAX отдаёт
`Content-Type: application/octet-stream` вместо JSON, и `maxapi` падает на
разборе ответа. Ловим это исключение и ретраим с экспоненциальной задержкой.

**Sliding window, а не сбрасываемый счётчик.** Счётчик, обнуляемый раз в
секунду, допускает всплеск в два лимита на стыке окон. Слот, освобождаемый
ровно через период, — нет.

**Настройки создаются лениво (`get_settings()` с кэшем).** Модульная
переменная `settings = Settings()` создаётся на импорте, и тест не может
подменить окружение до этого момента.

**Необработанное исключение в webhook отдаёт 200.** На 5xx платформа повторит
апдейт, который упадёт снова — получится бесконечный цикл вместо одной записи
в логе.

**`expire_on_commit=False` для сессий SQLAlchemy.** Иначе обращение к любому
полю объекта после commit вызывает новый SELECT, а в async это выстреливает
`MissingGreenlet` уже вне сессии.

**`upsert` вместо «прочитать и решить».** Два одновременных события от одного
пользователя иначе гонятся за вставку, и один из запросов падает на нарушении
первичного ключа.

**`name:` в compose-файлах.** Без него Compose берёт именем проекта каталог,
где лежит сам файл, то есть `docker` — контейнеры и тома получают чужие имена,
а после переименования каталога меняются снова.

**Значения из Gitea Variables чистятся от `\r`.** Переменная, заведённая через
веб-интерфейс, может прийти с переводом строки — URL склеивается с `\r` и
запрос уходит в никуда.
